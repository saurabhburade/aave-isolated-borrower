# Data and execution architecture

The application has four data boundaries:

1. Discovery verifies the local factory deployment, combines the official Ethereum Aave catalog with optional local market pins, and validates each selected venue on the fork. Pinned venues retain their bytecode and ERC-1967 implementation checks. Dynamic venues must have deployed code and expose the expected V3 provider/Pool binding or V4 reserve inventory before their full native reserves are read.
2. Quotes validate a complete collateral/debt basket against one venue. A quote is informational until the exact owner, salt, approvals, block, and native execution path have been simulated.
3. Execution encodes only the frozen `PositionFactory.createPosition` and `PositionAccount.execute` actions. The predicted account is the approval spender and the immutable owner is the payout recipient.
4. Portfolio reads are native account reads. Envio and factory/account logs are discovery and activity sources, with a chain-log fallback when the indexer is absent or behind.

Every identity is chain-qualified. Market identity is `chain/version/venue`; position identity is `chain/account`; a V4 reserve keeps its Spoke-local `reserveId` and Hub mapping. Global form assets use `Asset.tokenId = chain/token`; ambiguous same-underlying reserves require an exact reserve ID or an explicit `preferredDebtReserveIds` choice in the verified manifest. Bluechip defaults to Core USDC reserve 7, while retaining its separate Prime USDC reserve for explicit position operations.

Market browsing uses both public Aave GraphQL APIs. `/api/market-catalog` fetches only the selected source chain and caches market/reserve metadata for one minute, including token metadata, supply/borrow/collateral eligibility, and oracle USD prices. Form assets use a chain/token identity and are deduplicated by exact address. All selected collaterals and the debt token must be supported within a single market. `/api/market-rates` validates the filtered market IDs against that catalog, then batches reserve APY queries to V3 and V4 in parallel, caching successful results for 15 seconds. Failed providers are retried and do not hide the healthy provider. Invalid or missing rates remain unknown; valid zero rates can rank first.

Comparison row IDs are API catalog identities with a separate `executionMarketId` binding to a verified local venue, matched by source chain, protocol version, and address. Ethereum catalog markets receive a native execution identity automatically; no factory registration or manifest entry is needed. Testnet and other-chain entries remain excluded from local execution. A market absent at the fork block or incompatible with the adapters remains unavailable with its native validation reason. Multi-Hub V4 loans bind the request to the exact reserve used for the displayed indexed APY, preserving explicit local debt-reserve preferences. The cheapest indexed APY is the default after asset/version filters change; amount edits preserve a manual selection. V4 comparisons use base APY, honoring any locally configured preferred debt reserve ID. Position simulation reads the effective borrowing rate, including collateral risk premium, from the native post-action state before execution. The table shows Max LTV from collateral parameters (weighted by entered USD value for a basket). Health factor and actual LTV are estimated from entered amounts and the market’s own indexed prices: V3 weights collateral by its standard liquidation threshold; V4 uses its collateral factor. Disabled collateral contributes no backing. Missing amounts, prices or parameters remain unknown, and estimates never authorize execution. Native simulation replaces estimated position risk when available. USD input estimates use the API oracle price independently of simulation; they reflect indexed source-chain state, which can differ from a pinned fork.

Native `/api/markets` discovery still verifies contract identities and reserve support for execution. Its optional token metadata enrichment uses V4 `swappableTokens`, matched by source chain, address and decimals. API catalog inclusion never grants execution support.

The server fails closed when the local manifest, chain, bytecode, reserve inventory, or native simulation is unavailable. Missing debt, risk, or indexer rows are unknown-not zero.


The Borrow widget requests `/api/markets?summary=true` for factory-verified candidate identities. These candidates are marked unchecked; their venue and adapter checks run when selected, avoiding speculative RPC reads across the entire catalog. Quotes and review read only the selected market’s requested collateral/debt reserves, so an unrelated stale reserve cannot block the new position; V3 portfolio reads combine native user-configuration reserve IDs with account action history to retain disabled supplies, while V4 retains complete inventories; `/api/markets` retains a complete inventory for local tooling. Concurrent native inventory requests share a ten-second cache bound to the observed block hash, factory, market configuration and requested token basket. Failed reads are retried, and factory verification runs before cache reuse. Quotes are keyed by market, basket, owner and salt so changing markets cannot reuse another market’s execution approval. A successful wallet-bound selected-market quote includes its server-prepared signing plan. Opening review reuses that plan immediately; an expired or missing plan is refreshed. Position checking has a visible busy label, a bounded timeout and an explicit retry through Refresh. Wallet actions and transaction confirmation have distinct labels.

Portfolio discovery follows factory creation events and loads the dynamically discovered markets used by those accounts. A temporarily undiscoverable market leaves a visible unknown position rather than silently dropping its account.

Transaction completion waits for a successful receipt with one block confirmation. The UI then shows “Transaction confirmed” while polling the native position endpoint for up to 60 seconds. Completion requires a fresh read at or after the receipt block, bound to the same account, owner, market and chain. Temporary HTTP failures, absent positions, stale observations and unknown positions are retried. Dismissing review cancels polling; a bounded timeout retains the confirmed hash and offers Positions without enabling duplicate submission. This applies to position creation and management.

V3 portfolio discovery resolves native reserve IDs through `getReserveAddressById`, preserving gaps in reserve numbering, and includes every token from the account’s typed action history. It inventories the union across the owner’s accounts per venue instead of blocking each view on unrelated reserves. Missing discovery evidence falls back to a complete inventory. The returned market retains the full catalog asset list with reserve-qualified identifiers so management can still add new assets; management preparation reads existing position tokens plus the requested action tokens.
